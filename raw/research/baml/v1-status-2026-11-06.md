## 1. Release status

- **[Verified]** The v0 docs carry a notice: they document "BAML v0, the legacy DSL". BAML v1 is called "a separate, fully featured programming language in public beta". The notice gives no URL for the v1 docs. (S6)
- **[Verified]** The v1 toolchain ships as GitHub releases named "BAML Language" (tags `baml-language-<x.y.z>`). The v0 track ships as "BAML v0" (tags `0.226.x` / `v0.226.x`). (S2, S3)
- **[Verified]** Latest v1 releases: `baml-language-0.24.0` (2026-11-05T22:23Z), `0.25.0` (2026-11-06T03:22Z), `0.25.1` (2026-11-06T05:24Z). Also `baml-wrapper-0.3.0` and `0.3.1`. Release bodies only say "BAML language toolchain <version>". (S2)
- **[Verified]** Earlier v1 releases: 0.16.0 (2026-08-12) through 0.23.0 (2026-10-26), plus daily `0.23.1-nightly.*` builds. All have `prerelease: false`. (S2)
- **[Verified]** Latest v0 release: `0.226.3` (2026-10-28). PyPI `baml-py` is 0.226.3 (v0). PyPI `baml-bridge` and npm `@boundaryml/baml-bridge` are 0.25.1 (v1 bridge). (S2, S20, S21)
- **[Verified]** No tag or release named 1.0 or v1 exists. The version line is 0.x. (S2, S3)
- **[Verified]** Install path (v1): `brew install baml`, or the script at `pkg.boundaryml.com/install.sh` (PowerShell `install.ps1`), or `yay -S baml-bin`. The `baml` wrapper is a version manager for project toolchains. README adds `baml agent install`, `baml init`, `baml ide install --code`. (S4, S7, S10)
- **[Verified]** v1 docs site: developer.boundaryml.com (Book, Language Reference, Standard Packages, Language Bridges, CLI, Cloud). The get-started page shows the "Canary" toolchain. The CLI reference is indexed at v0.23.0, behind release 0.25.1. (S7)
- **[Verified]** Release notes: blog posts tagged "release" (0.19.0, 0.20.1, 0.21.0, 0.23.0). No post for 0.24.0 or 0.25.x found. (S12)
- **[Verified]** Blog post of 2026-11-05: the team puts "final polish" on the language and prepares "a 1.0 release". It calls the core language design "nearly complete". (S13)
- **[Verified]** Status words conflict. The v0 docs say "public beta" (S6). The homepage, explore page and the 2026-11-05 blog say "private beta" with a 45-minute founder call for access (S8, S9, S13). The quickstart says "early access" for the cloud platform (S10).
- **[Inference]** "private beta" probably applies to the full stack with Boundary Cloud; the open-source toolchain is publicly installable. Not stated explicitly.
- **[Inference]** v1 is not released as 1.0. It is a public, installable 0.x toolchain in beta, with a 1.0 announced as in preparation. This agrees with "very far along" in the owner report; it does not support "finished".

## 3. Positioning, users, licence

- **[Verified]** GitHub description: "The programming language for agents". README: looks like TypeScript, Rust-like type system, runtime types, typed and statically analyzed errors, green threads, built-in tests/evals, agent stdlib. Runs standalone or is called from TS, Python, Go, C#, Java and others. (S1, S4)
- **[Verified]** Homepage: "The hyper-observable programming language", one stack instead of 10+ tools. Sections: Build, Deploy, Observe, Improve, Adopt. Bridges to Python, TypeScript, Go, Rust, Java, Swift, C++. (S8)
- **[Verified]** Repo change "compile BAML MIR to Rust" (#5264) is between 0.23.0 and 0.25.1. The runtime has a VM, bytecode and a native backend. (S5)
- **[Inference]** BoundaryML positions v1 as a full language plus runtime for agent software, not as a general-purpose language. Target users: engineers who build AI agents and workflows.
- **[Verified]** Licence: repo is Apache-2.0. Pricing page: "BAML is free and open source"; local toolchain needs no Boundary server. (S1, S11)
- **[Verified]** Boundary Cloud: observability, team controls, governance; hosted, in customer cloud or on-premise. Pricing not announced; "coming later this year"; early access through Discord or founder call. (S8, S11)

## 5. Debug and replay

- **[Verified]** Homepage: the runtime records the program as it runs and sends it to Boundary Cloud, with no SDK or collector. One CLI to query traces and analyze errors. Tests sit in the same file as the code; an example makes a test per production ticket from S3. (S8)
- **[Verified]** 0.21.0 notes: runs are recorded in a shared format and are queryable with SQL, e.g. `baml query --local`. Relations: processes, spans, span_announcements, profiler. Per-call `$trace` options; input capture needs `inputs = true`. (S14)
- **[Verified]** 0.23.0 notes: an AI function call records as a single operation in traces. (S15)
- **[Verified]** Repo after 0.23.0: bridge traces record in the project so `baml query --local` finds them; old `baml_query` crates and DataFusion removed. (S5)
- **[Verified]** No use of "replay", "re-run", "mock", "fixture" or "deterministic" found on the homepage. The v1 get-started page names no replay. (S7, S8)
- **[Unknown]** Whether v1 can replay a recorded call or substitute a recorded model response in a test. See the earlier capture [debugging-replay-2026-11-06.md](debugging-replay-2026-11-06.md) for `F@parse` and `baml query` in code.
