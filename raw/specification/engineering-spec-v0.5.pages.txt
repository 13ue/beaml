 BEAML
 Language Engineering Platform — Specification v0.3
 Architecture baseline | 05 November 2026 | Design proposal, not an implemented system

 Scope: a statically typed LLM-oriented language targeting the BEAM, with a Rust-implemented compiler,
 a unified semantic database, language server, property testing, domain contracts, architecture rules,
 and privacy-preserving hyperobservability.


 Executive decisions
 • Rust compiler and CLI; generated Erlang/Elixir-compatible modules; Elixir/OTP runtime.

 • Lossless syntax tree, typed HIR, typed MIR, stable symbol IDs and incremental semantic queries.

 • LSP, formatter, linter, testing and architecture checks reuse compiler semantics.

 • Soundness boundaries: untrusted model responses must be validated; external Elixir calls are explicit
 trusted/checked boundaries.

 • All numeric targets below are proposed acceptance thresholds, not measured results.


 1. Product boundaries and non-goals
 BEAML specializes in type-safe model interaction and workflow orchestration. It is not a replacement for
 Erlang, Elixir or Gleam. The domain/architecture language extensions are optional modules, not
 mandatory boilerplate. Avoid claims that a compiler can prove arbitrary business correctness, LLM
 truthfulness, or behavior of foreign code.


 2. Language grammar and surface design
 program     = { import | type_decl | trait_decl | impl_decl |
                 client_decl | function_decl | property_decl |
                 context_decl | architecture_decl } ;
 type_decl   = ("type" | "newtype" | "class") IDENT type_params?
               ("=" type_expr | "{" field* "}") refinement? ;
 type_params = "<" type_param ("," type_param)* ">" ;
 type_param = IDENT | "const" IDENT ":" type_expr ;
 function_decl = "function" IDENT type_params? "(" params? ")"
                 "->" type_expr effects? block ;
 effects     = "!" ("pure" | "{" IDENT ("," IDENT)* "}") ;
 property_decl = "property" STRING "forall" bindings block ;
 architecture_decl = "architecture" IDENT "{" rule* "}" ;


 Expression grammar is Pratt-parsed; templates have their own interpolated expression parser and
 precise source spans. The complete lexical and expression grammar remains a v0.4 deliverable; this
 excerpt is intentionally not advertised as a complete parser specification.

 3. Type-system contract
 • Core: primitives, nominal newtypes, structural records, tagged ADTs, generics, exhaustive pattern
 matching, type inference for local expressions.

 • Traits: coherent global instance resolution; no overlapping impls in v1; associated types in phase 2.

 • Refinements: constant and interval proofs first; undecidable or unsupported predicates require explicit
 checked conversions.

 • Effects: explicit sets and effect-subset checking, with pure functions unable to call effectful functions.

 • Phantom types and typestate: Pending/Streaming/Validated/Complete states; affine ownership of
 stream handles later.

 • Const generics: restricted natural-number expressions; higher-kinded types, GADTs and type families
 are later extensions.

 • Schema reification: generic model outputs require a Schema witness, either monomorphized or passed
 as a typed dictionary.

 Trust-boundary invariant
 Untrusted<Json> --decode--> Parsed<T>
 Parsed<T> --validate--> Result<Validated<T>, ValidationError>
 Validated<T> --check refinement--> Result<Refined<T,P>, Error>


 Validated values certify conformance to a declared schema, not factual truth. Runtime validation may
 fail; provider/network errors are represented in the generated API. Optional fields must distinguish
 missing from explicit null when the schema requires that distinction.


 4. Compiler architecture and correctness
 .beaml -> lexer -> lossless CST -> AST -> resolved HIR
       -> type/trait/effect/refinement checking -> typed MIR
       -> codegen (Elixir/Erlang source + validators + metadata)
       -> BEAM compiler -> .beam


 Compiler implemented in Rust as a standalone executable invoked by Mix. Stable semantic IDs and
 source maps survive lowering. Typed MIR stores control flow, effects, validation obligations and
 instrumentation points. The first backend emits Elixir/Erlang-compatible source; direct BEAM bytecode is
 out of scope.

 Incremental query graph
 parse(file) -> lower(file) -> resolve(module)
 type_of(def_id) -> effects_of(def_id)
 mir_of(def_id) -> emit(module)
 references(symbol_id) -> rename_edits(symbol_id)


 Queries are deterministic with tracked dependencies and cycle diagnostics. Cache keys include compiler
 version, feature flags, schema capability descriptors and imported interface fingerprints. A warm-cache
 change to a prompt literal should not invalidate unrelated type queries.

 Compiler correctness obligations
 • Well-typed safe programs do not get stuck on language-level type mismatches (subject to explicit
 foreign and runtime effects).

 • Every lowering pass preserves the observable semantics of the supported core language.

 • Error recovery produces useful diagnostics without silently accepting ill-typed programs.

 • Compile-fail suites, MIR golden tests, differential tests, fuzzing and property tests are release gates.


 5. Language server and developer experience
 beaml-lsp uses the same semantic database as the compiler. It maintains overlays for unsaved buffers
 and reparses only affected syntax regions where possible. It supports incomplete and malformed code
 without crashing.

   Capability                          Acceptance behavior


   Completion                          Type-aware fields, traits, functions and prompt interpolation


   Navigation                          Definition, references, implementation, call hierarchy


   Refactor                            Rename with cross-file edits and collision checks


   Diagnostics                         Syntax, type, trait, effect, refinement, architecture


   Editor support                      Hover, semantic tokens, inlay hints, code actions, formatting


 LSP compatibility is verified against the published protocol version chosen for release. Editor plugins
 must not duplicate semantic analysis. All edits are versioned and rejected when the client document
 version is stale.

 7. DDD: domain types, aggregates, commands, events
 context Billing {
   newtype InvoiceId = UUID
   aggregate Invoice {
     id: InvoiceId
     status: InvoiceStatus
     invariant { total.amount >= 0 }
     command approve() requires status == Draft
       ensures status == Approved
     event InvoiceApproved { invoice_id: InvoiceId }
   }
 }


 DDD constructs are optional annotations with explicit semantics. Pure aggregate transitions can be
 statically analyzed; database atomicity, external side effects and distributed consistency require runtime
 and integration guarantees. Generated event schemas are versioned, with compatibility checks for
 breaking changes.


 8. ArchUnit-style architecture constraints
 architecture BillingRules {
   rule "domain is pure" {
     modules("billing.domain.**")
       .must_not_have_effects {network, database, llm}
   }
   rule "no dependency cycles" {
     packages("billing.**").must_be_acyclic()
   }
   rule "sensitive telemetry flow" {
     fields(annotated Sensitive)
       .must_not_flow_to(effect telemetry)
   }
 }


 Structural checks use the symbol/dependency graph; semantic checks use typed HIR/MIR and effect sets.
 Information-flow rules require conservative taint analysis and may be inconclusive at opaque foreign
 calls. Inconclusive results are surfaced, never presented as proven safe.

 10. Hyperobservability and privacy
 Instrumentation is compiler-generated with stable operation IDs, trace/span context, type/schema
 versions, effect metadata, validation-path identifiers and source maps. Logical workflow edges are
 distinguished from BEAM process links. Context propagation across process messages is explicit.

 • Metrics: provider latency, time to first token, tokens, cost estimate, retries, validation failure rate, field
 readiness and queue time.

 • Default telemetry captures metadata only; sensitive prompts, responses and field values are redacted
 or absent.

 • Replay stores explicitly permitted fixtures and recorded provider responses; it is not deterministic
 replay of arbitrary BEAM scheduling.

 • Telemetry exporters and logs are themselves treated as external effects; no sensitive field may be
 emitted without policy approval.

 15. Open design decisions and risks
 • Precise subtype relation for structural records and variance of generic parameters.

 • Trait coherence and orphan rules across packages; associated-type normalization.

 • Refinement predicate fragment and solver timeout/unknown policy.

 • Streaming field states and whether partial values may be revised before completion.

 • BEAM interoperability: opaque foreign effects, dynamic atom safety, serialization and process
 cancellation.

 • Effect handler strategy: explicit handler dictionaries first, algebraic continuations later.

 • Architecture taint analysis precision and waiver governance.

 • Schema evolution and compatibility guarantees for domain events and generated APIs.


 16. Normative language for future specifications
 MUST denotes a release-blocking requirement. SHOULD denotes a recommended default with
 documented exceptions. MAY denotes optional functionality. No performance number is a claim of
 achieved implementation performance until benchmark evidence is attached. A language feature is not
 stable without documented syntax, typing, dynamic semantics, diagnostics, interoperability behavior
 and tests.

 Version 0.3 is an architectural baseline. Next specification deliverable: formal typing judgments,
 operational semantics, trait-resolution rules, typed MIR invariants, exact query invalidation protocol and
 complete EBNF.

 BEAML v0.4 — Phoenix LiveView & Type-Aware HEEx
 Normative extension to Engineering Specification v0.3 | 05 November 2026 | Status: proposed design; no
 implementation or benchmark is claimed. The preceding v0.3 specification is retained unchanged. This appendix
 defines an incremental, compiler-driven UI contract layer rather than a new rendering language.


 21. Architectural boundary and ownership
 BEAML owns domain types, application commands, validation, effects, and optionally UI contracts. Elixir owns
 Phoenix LiveView callbacks, HEEx markup, components, routing, Ecto adapters, and OTP infrastructure. The
 boundary is a generated, versioned Elixir ABI with explicit decoding and validation. Direct construction of ordinary
 Elixir structs does not confer trusted BEAML type status.

 BEAML domain + application contracts
         | schema / contract descriptors
         v
 Generated Elixir API + Phoenix adapter
         |
 Phoenix LiveView + HEEx templates
         ^
 Type-aware HEEx analyzer <--> shared semantic query engine


 22. Contract syntax: assigns, events, forms and components
 Illustrative BEAML syntax, to be formalized in the grammar. UI contracts are optional and may be attached to a
 LiveView, component, or command. External data enters through explicit decoder functions.

 ui InvoiceEditor {
   assigns { invoice: Invoice; form: Form<CreateInvoice.Input>; busy: Bool }
   event "validate"(payload: FormParams<CreateInvoice.Input>)
   event "save"(payload: FormParams<CreateInvoice.Input>)
   event "delete"(payload: { id: InvoiceId })
   component InvoiceCard {
     prop invoice: Invoice
     prop compact: Bool = false
     slot actions: Slot<InvoiceId> optional
   }
 }

 Semantics: event names are literal discriminants; payloads are decoded from untrusted string-keyed maps; assigns
 are checked at render entry and across recognized assign transformations. Conditional branches, dynamic keys,
 and arbitrary Elixir metaprogramming require explicit fallback diagnostics rather than false guarantees.


 23. Generated Elixir / Phoenix adapter
 alias MyApp.BEAML.InvoiceEditor, as: Contract

 def mount(_params, _session, socket) do
   {:ok, Contract.assign(socket, invoice: invoice,
     form: Contract.form(), busy: false)}
 end

 def handle_event("save", raw, socket) do
   with {:ok, input} <- Contract.decode_event(:save, raw),
        {:ok, invoice} <- CreateInvoice.execute(input) do
     {:noreply, Contract.assign(socket, invoice: invoice)}
   else
     {:error, error} -> {:noreply, Contract.put_error(socket, error)}
   end
 end

 The generated ABI must expose stable typed descriptors, decode_event/2, form/0, change/2, assign/2 and field
 references. Event decoding does not assume that browser payloads are valid. Return values remain explicit {:ok,
 value} / {:error, error} at the Elixir boundary.

 24. Type-aware HEEx analysis
 A dedicated analyzer uses the official Phoenix/HEEx parser and available Elixir semantic information, mapped to
 BEAML HIR symbol IDs and source spans. It must not rely on regex over template text. The initial analysis is sound
 only for the supported, statically analyzable HEEx subset.

 <.input field={Contract.field(@form, :amount)} />
 <.invoice_card invoice={@invoice} compact={true}>
   <:actions :let={id}><.button phx-click="delete"
     phx-value-id={id}>Delete</.button></:actions>
 </.invoice_card>

 Checks: (a) @assign presence and declared type, (b) field names and refinement metadata, (c) component prop
 and slot shape, (d) literal phx-event name and payload contract, (e) missing event handlers where statically
 knowable, (f) unsafe dynamic boundaries flagged as unknown. In particular, phx-value-* values arrive as strings and
 require decoding; an InvoiceId is never inferred from a raw browser string.

 26. Forms and validation semantics
 Three states are distinct: RawFormParams -> ParsedInput -> Validated. Partial form editing returns field-level
 diagnostics without claiming a fully valid aggregate. Server-side validation is authoritative. Client-side constraints
 generated from refinements are convenience hints only. Optional, missing, empty-string and null values must have
 separately specified semantics.

 CreateInvoice.form()
 CreateInvoice.change(form, raw_params) # partial, field errors
 CreateInvoice.decode(raw_params)       # Result<Validated<Input>, Error>
 CreateInvoice.execute(validated)       # Result<Invoice, DomainError>

 BEAML v0.5 — Observatory & Information Flow Security
 Normative proposed extension to v0.4 | 05 November 2026. All earlier chapters are retained. This appendix
 introduces compiler-generated observability and information-flow controls. No security proof, benchmark result, or
 implemented feature is claimed.

 33. Security objectives and non-guarantees
 The primary objective is to prevent unauthorized sensitive-value flows across compiler-controlled boundaries by default.
 A compiler alone cannot promise that secrets never leak: arbitrary Elixir, NIFs, compromised hosts, side channels,
 explicitly authorized recipients, and misconfigured infrastructure remain in the threat model. Therefore all assurances
 are scoped, testable, and tied to a declared trusted computing base (TCB).

 34. Classification and typed labels
 type Email = String @pii(email)
 type AccessToken = Bytes @secret(credential)
 type CustomerId = UUID @confidential(customer)

 class Customer {
   id CustomerId
   email Email
   notes String @pii(free_text)
 }

 fn display_name(c: Customer) -> String @pii(free_text) {
   return "Customer: " + c.email
 }

 The label is attached to the value and propagates through string interpolation, concatenation, formatting, collections,
 records, variants, maps, errors and derived values. A bare String return annotation must not silently erase a sensitive
 label; the compiler rejects it or infers the sensitive result. Implicit conversions to less-restricted labels are forbidden.

 35. Information-flow lattice and effect constraints
 Use a label lattice with dimensions confidentiality (public, internal, confidential, secret), data categories (PII kinds,
 credentials, financial, health), and allowed purposes/recipients. Join combines the restrictions of all inputs. The core
 typing judgment is Gamma; pc |- e : T @ L ! E. The program-counter label pc tracks implicit flows through
 secret-dependent branches; pure value-label propagation alone is insufficient.

 label(join(a,b)) = join(label(a), label(b))
 if secret_condition { emit("yes") } else { emit("no") }
 // Both outputs carry the implicit-flow restriction from pc.
 // Sink check: can_flow(label(value), sink_policy, context) == true

 Public error strings, branch-dependent logs, timing, response sizes, and cardinality can disclose information even
 without raw secret bytes. For v1, reject secret-dependent output branches to public sinks where analyzable; explicitly
 document that timing and other side channels are not comprehensively eliminated.

 36. Sink policies and explicit release
 sink telemetry.metadata accepts Public | ApprovedAggregate
 sink browser.render accepts Public | UserScopedPII
 sink llm.external accepts Public | ExplicitlyApprovedPII
 sink http.external accepts Public | RecipientScopedData

 fn masked_email(x: Email) -> String @public
   ! {declassify(reason: "display masked email")} {
   return privacy.mask_email(x)
 }

 Declassification is a privileged capability, not a cast or arbitrary annotation. Require a named policy, justification,
 principal/purpose, reviewer-controlled allowlist, audit event containing only metadata, and a generated callsite identifier.
 Prefer vetted operations (masking, irreversible tokenization, aggregation) over free-form declassification. A mask is not
 automatically anonymous; the declassification rule must specify its leakage budget and output guarantee.

 37. Elixir / Phoenix trust boundaries
 BEAML-generated public APIs use opaque handles or sealed validated values where possible. At Elixir interop
 boundaries, treat unknown functions as potentially leaking unless they are in a reviewed effect/taint manifest. Dynamic
 dispatch, macros, reflection, NIFs, and untracked dependencies are UNKNOWN or blocked in strict mode. Ordinary
 Elixir structs do not enforce secrecy. HEEx analysis checks rendering, assigns, component props, and event payloads;
 legitimate user-scoped PII display requires explicit authorization, not global declassification.

 ui CustomerProfile {
   assigns { customer: Customer @visible_to(owner_or_admin) }
   render_policy { require principal.can_view(customer.id) }
 }
 // @customer.email rendered only after authorized view policy.
 // No PII in phx-value-* attributes, URLs, debug inspect or flash.


 38. Secret handling and cryptographic boundaries
 Secrets are sourced from a secret manager or runtime environment, not embedded in .beaml source or compiler
 artifacts. Runtime representation should minimize copies, prevent routine inspect/serialization, and zeroize where
 feasible; BEAM garbage collection prevents a blanket memory-erasure guarantee. Encrypt at rest and in transit, use
 least-privilege access, rotate credentials, and disable crash-dump/core-dump secret exposure where operationally
 feasible. Redaction is defense in depth, not the primary control.


 Observatory — operational specification
 39. Capture architecture and data ownership
 BEAML compiler instrumentation -> Phoenix/OTP telemetry adapter -> local redaction and policy enforcement ->
 OpenTelemetry Collector -> storage. Deployment modes: local, self-hosted, and optional managed. The default
 self-hosted reference deployment stores traces/events in ClickHouse, application/project metadata in PostgreSQL, and
 optional encrypted replay artifacts in S3-compatible storage. A small deployment may store traces in PostgreSQL
 initially. No remote exporter is required.

 40. Telemetry event schema
 ObservationEvent {
   event_id: UUID; trace_id: TraceId; span_id: SpanId
   parent_span_id: Option<SpanId>; process_id: OpaquePid
   semantic_id: DefinitionId; source_map_id: SourceMapId
   event_kind: EventKind; timestamp: Instant
   duration_ns: Option<Int>; outcome: Outcome
   attributes: Map<String, PublicTelemetryValue>

 45. Release policy and rollout
 P0: annotations, label propagation, strict sink checks, generated redacted telemetry, explicit unknown interop
 diagnostics, minimal Observatory with OTLP + Postgres. P1: ClickHouse, process graphs, policy-aware HEEx analysis,
 declassification approvals, security manifests and CI gates. P2: advanced implicit-flow analysis, vetted
 masking/tokenization, optional encrypted replay, distributed lineage and stronger formal verification. Default for
 production: fail closed for unclassified sensitive egress, payload capture disabled, and no implicit declassification.

 46. Definition of done
 Each security rule needs syntax, formal flow rule, static/dynamic enforcement boundary, positive and negative tests,
 diagnostic code, interop behavior, threat-model limitation and operational runbook. Security status is reported as
 PROVED (within formal model), RUNTIME_ENFORCED, TESTED or UNKNOWN; no blanket no-leak claim is
 permitted.
