Sperre 3 (zwei Literale vertauscht, DL-140/DL-161) kann der Build nur sehen, wenn er die alte Literal-Tabelle kennt. Heute steht im Code nur die neueste. Woher kommt die alte?

// VORHER: Channel v1, 5 Zeilen mit "app" in Production
enum Channel {
  Web = "web"
  App = "app"
  Unknown(String)
}

Option A · alte Deklaration bleibt im Code bis SQUASH (Default, Lesart von DL-155)

// Option A (gebaut als Default): die alte Deklaration bleibt stehen, bis keine v1-Zeile mehr existiert.
// Der Build kennt so die alte Tabelle und sieht Sperre 3 (Tausch). Fehlt v1 trotz migrate: lauter Fehler.
enum Channel v1 {
  Web = "web"
  App = "app"
  Unknown(String)
}

enum Channel v2 {
  Web = "web"
  Mobile = "mobile"
  Unknown(String)
}

migrate Channel v1 -> v2 {
  map "app" -> Mobile
}
BuildKennt v1 und v2, prüft jede gespeicherte v1-Zeile gegen beide Tabellen. Sind keine v1-Zeilen mehr da, sagt der Build: „Channel v1 has no stored values; remove the declaration and the step (SQUASH)“. Der Code ist die ganze Geschichte.

Option B · nur die neueste Tabelle, der Schritt beschreibt die Änderung

// Option B: nur die neueste Tabelle; der Schritt nennt jede Literal-Änderung selbst.
// Vergisst jemand eine Zeile, sieht der Build den Tausch nicht (Lücke).
enum Channel v2 {
  Web = "web"
  Mobile = "mobile"
  Unknown(String)
}

migrate Channel v1 -> v2 {
  map "app" -> Mobile
}
BuildKürzer. Aber ob "web" gestern Web hieß, steht nirgends mehr; ein vergessener map fällt nicht auf. Die Geschichte ist nur noch in der Datenbank.

Option C · alte Tabelle aus einer Lock-Datei oder dem letzten Build

BuildDer Compiler schreibt bei jedem Build die Tabellen in eine Datei neben die Quelle und vergleicht beim nächsten Mal. Funktioniert, aber die Wahrheit liegt dann in einer Datei, die nicht die Quelle ist; bei zwei Entwicklern zwei Dateien.

Dasselbe gilt später für type Amount v1 { … } neben type Amount v2 { … }: die alten Konstruktor-Regeln bleiben lesbar, bis Production leer ist.
