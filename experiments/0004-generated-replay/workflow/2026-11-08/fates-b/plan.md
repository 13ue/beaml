## 4. Answer-class parts: stop for the OWNER (no recommendation)

Undo cost question: "if this is wrong, what does it take to put right?" For these parts: nothing. A deleted row or a removed
hidden value cannot be restored by BEAML, and the wrong outcome reaches the app's users and the data subjects.

**A1 · b2b: BEAML deletes STORED ROWS after N days (DL-163 effects 1, 2, 3, 5).** The OWNER decided *that* BEAML deletes
(DL-163, By: 13ue). Open and Answer class: *which* rows die, *when*, *who* runs it.
- observed: DL-163 chose B; no code deletes today; no time key in any record or snapshot; the 0005 table has `inserted_at`
  (host-written, Ecto default); the top-level RETIRE LINE today keeps RESPONSE RECORDS in the file (DL-057).
- observed: the language team split on this (W2 "the build never deletes", W1/W3 "retention is language policy").
- inferred: `inserted_at` is the host's clock and the host's column; a host that rewrites rows (backfill, restore) resets it.
- inferred: a core time key written by `db.put` changes every writer and the record format (draft 5, DL-165).
- inferred: a deletion run by the build would run on a developer machine against production (DL-151 live read).
- inferred: a deletion run by generated code on a schedule (D046, Oban) deletes with no human present.
- unknown: whether deletion also covers RESPONSE RECORDS and ENTRY RECORDS of the operation (tension with DL-057).
- unknown: whether quarantined rows are deleted after N days or kept until the quarantine is lifted.
- unknown: legal hold, backups, replicas: whether "deleted" must reach them.
- asked: nothing yet in this plan.
- Challenges: a clock skew or a wrong time zone deletes early; a restored backup brings rows back that a later run deletes
  again (DL-056 "a record that appears again blocks"); a dry-run count and the real run see different instants; an
  unattended night run that holds a database URL could delete.

**A2 · b1c: eager removal of hidden values on `redact f` (DL-111, QF-9).**
- observed: DL-111 chose eager removal (By: 13ue); QF-9 options A host function at deploy, B `--stored` writes a redacted
  copy, C read side only (contradicts DL-111); the compiler cannot write production (DL-151).
- observed: `value_sha256` covers `redacted` and `value`; a removal changes the digest, and DL-164 blocks a wrong digest.
- inferred: a removal must rewrite the digest, so it is a writer of records, not only a deleter.
- unknown: whether D039 (hash or encrypt) applies to the removed value (a hash keeps a trace; "removal" may mean "replace
  by hash").
- unknown: whether spans and logs already hold the value (DL-112 guards the code path, not old exports).
- Challenges: a removal that misses one store (rows vs RESPONSE RECORDS vs ENTRY RECORDS) leaves PII and reports success;
  a removal on the wrong field destroys data that no fate can bring back.

**A3 · the age source for b2a (QF-4).** It decides which production rows A1 later deletes, so it carries A1's class.
- observed: options A per-value time (row column or core key), B per line from first deploy, C host delete step.
- unknown: which instant counts (write time, last update, capture time of the record).
